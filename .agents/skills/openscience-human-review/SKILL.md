# Operate and assess a research conversation

Read the case START, 01, 03 and 04, its preparation manifest and frozen `design-basis/` references. For a new package use the shared [contract](../building-openscience-cases/references/operating-contract.md), [evidence matrix](../building-openscience-cases/references/evidence-collection.md) and [operator checklist](../building-openscience-cases/references/operator-checklist.md). Current user instructions take precedence; preserve changes as prospective decisions rather than rewriting earlier evidence.

## 1. Allocate and bind before launch

Ask the user to allocate Plan approval, scope questions, research extensions, recovery decisions and final acceptance to the user, operator or a specified split. Record concrete limits, run budget, restart allowance, operator-recovery limit and Reproduction authority. If the user already explicitly allocated these for this exact run, restate and record them instead of asking again. Starting a case or granting command permissions alone does not allocate scientific decisions.

Discover the actual project/session IDs, workspace, native interfaces and current model/runtime settings. Preserve the configured choices. Verify auto-review before submission, after session creation and before scientific execution. Verify capture and saving before required UI checkpoints; keep the OpenScience window maximized for evidence captures. Resolve missing launch conditions before sending, or record an explicit evidence exception within the user's authority.

Keep independent references and evaluation documents outside the scientific workspace and inspect actual access boundaries. Submit only 01, real attachments and necessary verified scientific environment facts. Use a fresh attempt identity and directory; uncertain submissions require status queries, not duplicate prompts.

## 2. Plan and make real decisions

Use the native **Plan first** action. A CLI/API is equivalent only when the installed version is verified to transmit native planning intent. Planning words alone do not prove this. Save the submitted message and intent, initial native Plan, version and pending approval state.

Resolve visible questions using the shared checklist, even when a pending-question list is empty. Preserve the selected answer and actual acceptance; a preselected option is not a submitted answer.

Assess the first Plan before feedback: scientific validity, coverage of the research question and feasibility of a useful first answer. Accept justified alternatives. Propose necessary revisions without expanding the investigation into an old fixed package. Identify native Notebook execution and traceable outputs as operating conditions at Plan review for computational work, rather than secretly scoring an undisclosed constraint.

Prepare stage-specific independent checks while reviewing methods. Record the decision-maker's approval for the exact version and freeze checks at approval, before inspecting resulting estimates. Perform and verify native approval and execution start. A feedback request, chat-only plan or idle turn is not an approved execution Plan.

## 3. Follow execution and native review together

Work from the [operator checklist](../building-openscience-cases/references/operator-checklist.md). While an authorized phase is active, read fresh execution, Reviewer, permission and question state; prefer supported events, otherwise use bounded polling. Give useful progress updates and continue until a real stopping condition. The skill is not a background service.

Capture input/run/artifact changes and actual native review events as they happen. Verify screenshot files were saved. Preserve findings, exact before/after versions, affected reruns and re-reviews. Record product verdict separately from external assessment. Main-agent idle does not establish that review or correction is finished.

Allow routine native corrections within the agreed task. If recovery fails or the agent stops without the agreed answer, first retain the failure and verify correction activity has ended. Within the recorded recovery authority and budget, send a focused operator prompt describing the evidenced blocker and outstanding commitment; verify subsequent actions. Label it operator-assisted recovery. Reference values, code or method fixes constitute additional scientific assistance and require the corresponding authority. Never turn assistance into retrospective autonomous success.

For finalization/revision-conflict failures follow the contract's bounded new-session rule, preserving the failed attempt. Do not repair product code as part of a scientific case.

## 4. Assess, extend and reproduce

Freeze stable outputs after both execution and relevant review/correction activity settle. Independently assess the agreed answer and methods, not a hidden reference package. Preserve incomplete and unsupported outcomes.

Submit acceptance or extension decisions to their allocated owner. A useful extension must answer an actual unresolved research question; record it as a new stage with explicit message/Plan lineage. Wait for the preceding stage to settle before sending it. Do not assume that one session means one task for the product's correction guards.

For authorized Reproduction, freeze the exact target and comparison rules before replay, save native preview, run the declared process, and retain receipts, logs and actual per-output results. Distinguish captured-inputs/end-to-end from checkpoint/downstream-only; record what is unavailable. An external rerun is a different operation.

## 5. Handoff and completion

Maintain an external handoff after significant changes: case/protocol/attempt/stage, session/run IDs, actual settings, authority and limits, Plan/artifact versions, execution/review/correction states, pending questions/decisions, budget/restarts/recovery counts, evidence locations, missing captures and next authorized action. Re-query the application after resuming; do not infer current state from an old note.

Stop only on completion within the authorized scope, the user's stop, an allocated decision requiring input, an exhausted budget or a demonstrated blocker after permitted recovery. State what still runs. Never imply monitoring continues after ending a turn without an actual configured mechanism.

Report research usefulness, scientific validity, product-feature evidence and Reproduction consistency separately. Record all attempts and interventions. A documentation-only request ends after validating the documents and makes no live case claim.
