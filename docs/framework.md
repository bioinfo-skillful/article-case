# Framework 2.0.0: research direction to supported answer

The case begins with a question and enough context to be useful. OpenScience investigates feasibility, clarifies meaningful uncertainties and proposes a bounded first Plan. The operator assesses that proposal; the allocated decision owner approves an exact version. Execution and native auto-review then develop the answer. Once they settle, a real research decision determines whether to stop, extend or replay a selected artifact.

The [operating contract](../.agents/skills/building-openscience-cases/references/operating-contract.md) is the authoritative procedure. The [operator checklist](../.agents/skills/building-openscience-cases/references/operator-checklist.md) keeps attention on actual UI questions, approvals, execution, review and evidence.

| Earlier preparation style | Conversation framework |
|---|---|
| Detailed initial methods and fixed file packages | A research direction with justified methods and output choices developed in the Plan |
| Preset full-task scientific checking rules | Validity principles at launch; detailed checks frozen for the approved stage before estimates are inspected |
| Delivery measured against the inherited package | Delivery measured against actual approved scientific commitments |
| Operator approval assumptions | Explicit assignment of five decision classes before each run |
| One large predetermined assignment | A bounded first answer and optional evidence-driven extensions |

The four separate outcomes are research usefulness, scientific validity, product-feature evidence and native Reproduction consistency. Flexibility affects prospective scope; it does not relax validity or erase unmet promises. Native automatic correction, agent self-repair, operator recovery and scientific assistance have different attribution.

Planning, Notebook execution, input/run/artifact provenance, runtime auto-review and Reproduction remain feature objectives. Their success is established by actual events and artifacts, not by a long prompt that mentions them. A naturally successful run may never exercise automatic correction. A justified qualitative first stage may not need Notebook computation. Record these limits instead of manufacturing events.

K-Dense examples inspired realistic scientific context, not a required scientific answer or a claim that their original prompts were equally open-ended. The new NHANES opening retains our smoking/depressive-symptom topic and cycle; GBM retains the landscape question. Neither inherits reference numerical results.

This release validates preparation and documentation. It does not claim new scientific runs, repaired application defects, or product reliability improvements.
