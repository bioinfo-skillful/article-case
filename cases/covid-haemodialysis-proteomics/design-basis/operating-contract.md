# Research conversation operating contract

Framework **2.0.0** · effective 2026-09-16 · prospective preparation and operation.

This is the shared behavioral authority for both skills. Terms are in [CONTEXT](CONTEXT.md), collection rules in [evidence-collection](evidence-collection.md), and the working checklist in [operator-checklist](operator-checklist.md). The [checklist adaptation](checklist-alignment.md) explains changes from the preserved v0.2 original; historical protocols remain historical.

## Roles, information and authority

| Role | Responsibility | Information boundary |
|---|---|---|
| OpenScience scientific agent | Clarify, plan, acquire sources, execute, self-check, communicate and repair | Research opening, actual attachments, approved requirements and ordinary scientific context |
| Built-in Reviewer | Review and guide corrections at native product boundaries | Actual native scope and accessible context, established by records rather than assumed |
| External operator | Operate controls, assess Plans, retain evidence and independently verify science | Preparation/evaluation materials and permitted native records; private reference work stays outside the scientific workspace |
| User / allocated decision owner | Decide scope, approve Plans, authorize extensions/recovery and accept results | Concrete proposals, exact versions and evidence-backed assessments |

Before **each run**, explicitly allocate five decision classes: Plan approval; scientific scope questions; research extensions; recovery including restart/operator prompts; final acceptance. Each entry names user/operator/split, limits and the escalation boundary. Record Reproduction authorization, total budget and restart/recovery allowances too. Existing explicit allocation for the same run is reusable. Unallocated choices remain pending; an operator may inspect and prepare a proposal but cannot assume the decision.

Command permission, scientific decision authority and product Plan approval are distinct. Delegation permits the operator to decide within bounds; it does not let an approval for one version stand in for a different version. Persist every actual decision and native action.

## CP0: a bounded direction, not a predetermined answer

Freeze the question, motivation, indispensable constraints, real initial inputs, allowed sources, feature objectives, authority allocation, budget and stopping rules. Leave unresolved scientific choices for discussion and planning. Record what source/metadata inspection is allowed before approval; it does not authorize substantive unapproved analysis.

Keep the current configured models, runtimes, routing and permissions unless the user directs a change. Discover enabled/runnable/execution-authorized states separately. No installed language is a universal requirement. Verify native auto-review and the means of saving evidence before submission, after new-session creation and before execution. If a required capability cannot be verified, retain the actual blocker and seek only the missing decision; do not silently declare the feature exercised.

Establish an external evidence root outside the scientific workspace. Directory separation alone does not prove access isolation: inspect actual access and disclose limitations. Reference answers and external scoring are not scientific-agent input. Published examples are assessed references, not ground truth.

## CP1: question, Plan, justified commitment

Send the opening through native Plan first; verify the persisted message intent and session binding. Current UI or supported native CLI/API is acceptable within user instructions. Check installed behavior rather than relying on an old field name. Save the entire first Plan, immutable version or snapshot hash, context and pending state before feedback.

Assess three axes: scientific validity; coverage of the stated question; feasibility and usefulness within the agreed resources. Record reasonable alternatives and unknowns. Feedback should address a demonstrated validity issue, unmet explicit requirement or real blocker. Formatting preference and hidden reference methods are not failures.

For the selected stage, prepare an assessment contract: question/estimand or qualitative claim; justified population/scope; method and assumptions; promised output content; claim slots; independent verification method and its self-check; comparison keys, fields, tolerances and applicability; expected execution evidence. Derive it from the proposed Plan, finalize against the approved version, and timestamp it before inspecting resulting estimates. If immediate execution starts on native approval, prepare criteria beforehand and leave numerical results unread until the contract is frozen. Results already inspected require disclosure; do not claim prospective checking.

The allocated owner approves the exact Plan. Perform the native action, read back approval and verify actual execution. Preserve feedback chains and version differences. Acknowledgment, a question-card answer, command permission and approval of a revision request do not substitute for this event.

## CP2 / CP3: execution with runtime auto-review

For computation use native Notebook execution and capture actual source bytes, code/order, parameters/seeds where relevant, dependencies and input → run → artifact/version relationships. A later exported script can aid delivery but cannot replace execution evidence. Qualitative research need not invent a computation merely to use Notebook.

Observe auto-review at the product's actual boundaries throughout each authorized stage. Preserve trigger, scope, actual accessible/read evidence, findings, before/after versions, affected executions, re-reviews and termination. Do not split turns or force a review after every Plan step to manufacture coverage. An observed step link is evidence; an assumed link is not.

Distinguish four mechanisms: agent self-repair; native automatic correction; operator recovery prompt; operator scientific assistance/direct repair. A natural case without a correction only demonstrates the observed review path. Optional injected-error exercises need separate authorization and identities; they do not improve the natural case's counts.

The native verdict and external finding validity/scope assessment remain separate. A warning or FAIL can be correct product behavior. Read failure, no observable read, outdated review and stopped correction are different states. Preserve the exact evidence before assigning cause.

When native recovery ends without delivery, retain the result and check that no correction is still active. Within allocated authority and budget, an operator may send a focused recovery prompt stating the evidenced failure and unfinished commitment. Preserve its text, version links, subsequent actions and resulting verification. Numerical answers, supplied code or changed methods are scientific assistance, not merely a nudge. If recovery is outside authority or exhausted, provide a concrete decision and hold the affected work.

## CP4: a useful answer and a genuine next question

Check execution, review and correction terminal states separately. Freeze the first complete delivery at its actual occurrence with all preceding/concurrent reviews; it may already include automatic repairs. Freeze final versions after activity settles; partial/failed states may be archived without being called complete.

Evaluate four dimensions separately:

1. Research usefulness: does the stage answer its agreed question with usable, bounded conclusions?
2. Scientific validity: independently verified inputs, methods, structure, values/claims and presentation, with uncertainties stated.
3. Product-feature evidence: actual planning, Notebook/provenance, artifacts and Reviewer behavior within observed coverage.
4. Reproduction consistency: native replay of a declared process; handled below and distinct from truth.

Construct independent references from approved methods and captured inputs, not copied fitted answers. Validate the reference itself and report shared dependencies. Check valid alternative methods for comparability before calling different values wrong. A confirmed error remains a failure of its scope; unresolved checks remain unresolved. Do not relabel promised deliverables optional after failure.

After the stage and its review settle, the allocated owner may accept the answer or choose a scientifically useful extension based on an unresolved question. Record the extension as a new research stage, including new request/task and Plan lineage; obtain exact-version approval and checking rules for its computation. A new request in the same session is not automatically part of the previous correction task. Keep extensions distinct from corrections of existing commitments.

## CP5 / CP6: declared native Reproduction

At launch allocate authority and budget for this phase; select the actual target and freeze its immutable version, captured-input scope, expected comparisons and allowed recovery before replay. Prefer **original captured inputs / end-to-end** within the declared generating process. This does not automatically include a fresh network download or the entire study. A checkpoint replay is **downstream-only** and reported separately.

Save preview, recipe, intended steps, dependencies/environment locks and critical/noncritical gaps. A preview success is not execution success. Critical missing dependencies block the claimed replay; save the gap rather than substitute old outputs. Record actual process/kernel/workspace isolation and whether old values/context are accessible.

Run the authorized native operation and save success or failure, receipt if generated, logs, completed steps and each output's expected/actual hashes and sizes. Preserve byte, content and scientific raw comparison states separately, including not generated or not applicable. A missing scientific comparison is not scientific PASS. Use domain-specific policies only for appropriate data; ordinary continuous marker tables use ID-aligned numerical checks with prospective tolerances.

Track output identity separately from retention/exportability. Collect genuine new bytes where available. If matched files are not retained, retain the actual checksum/size record and limit external file-comparison claims; never copy old files as replay outputs. Keep native replay, code reconstruction, external rerun and operator-assisted recovery separate. Identical results may still be scientifically wrong.

## Stopping, failure and archive

For finalization or revision conflict: retain the exact error, session/version/state and available outputs; settle the failed attempt within allocated authority; restart in a fresh session only within the recorded budget and allowance. Repeat launch checks and native Plan first with a newly approved Plan. Keep every attempt separate and do not retry publication or patch the application as part of this case. At zero/used-up allowance, retain partial evidence and escalate the bounded decision. No application restart is implied.

Stop on user instruction, terminal authorized work, a required unallocated decision, exhausted budget or demonstrated blocker after permitted recovery. At a hold, say what is still active and what decision is needed. The operator skill does not continue running after its agent turn ends.

CP7 preserves all attempts, versions, omissions, decisions and display choices. Use event times with zones; use interval unions for overlapping activity and mark unknown active time as missing. Do not infer general success rates from a few cases or count cells/retries/findings as independent cases. Changing the protocol prevents treating these as fixed-prompt reruns of historical cases.
